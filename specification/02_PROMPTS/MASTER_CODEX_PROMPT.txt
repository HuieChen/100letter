你现在要在现有 Solmere 项目上，从零到一实现一个可完整游玩的高完成度 MVP。这个 MVP 不是按钮原型，不是视觉小说式点点点，不是只证明逻辑能跑，而是一个短体量、约 30–45 分钟、拥有明确美术风格、实际操作、完整音画反馈、连贯谜题、可重玩的 Steam Demo 级游戏切片。

- 00_README_FIRST.md

如现有仓库已有引擎、目录结构、存档系统或 UI 框架，必须优先在原系统增量开发，不得无理由推翻重建。若是空仓库，默认 Godot 4.x。

====================
二、绝对不可违反的素材规则
====================
1. `00_USER_ASSETS_LOCKED/` 内所有用户素材逐像素视为 LOCKED。
2. 不允许 AI 重绘、融图、风格化、inpaint、补全、换脸、改服装、改动作、改配色、改轮廓、改建筑结构。
3. 主角必须保持用户最初上传的动作与造型，不生成“新动作版主角”。
4. NPC 尘缘同样原样使用。
5. 用户给出的棋摊、公交站、塔罗店、观景台、居民楼、邮局、社区中心都不许重画。
6. 引擎内只允许：原样加载、等比缩放、平移、显示隐藏、透明淡入淡出、点击热点覆盖。
7. 缺失素材只生成“新的独立资产”，绝不把用户资产融合进生成图。

====================
三、艺术方向
====================
最终游戏必须是 2D、平面、简约、几何概括、色块清晰、低细节、高可读，不要写实，不要厚涂，不要 3D 渲染感，不要电影灯光，不要 AI 常见的高密度装饰。

主风格优先级：
1. Faefever：手绘 2D、舞台式 point-and-click 场景、简化空间、清晰 silhouette、角色和场景都服务于读图与交互。
2. Crushed in Time：只取形体概括、几何化、轮廓清楚、低细节高识别度；不要取 3D 材质、体积、真实光照。
3. 用户现有建筑资产：正面、色块、几何、少纹理。

整体情绪：Solmere 的夏日海边小镇，温暖、清新、轻微慵懒，底层有苦甜和不安，但绝不整体转成黑暗侦探片。后期哲学感来自内容和选择，不来自突然变黑红色调。

视觉目标：
- 每个画面只有 1 个主要视觉焦点，最多 2 个次焦点。
- 背景简化，不堆细小装饰。
- UI 使用纸张、文件夹、邮局标签、简洁色块。
- 交互对象边缘与背景分离清楚，但不要发光描边答案。
- 新生成背景与物品保持 2D 平面正视或轻微 3/4 视角，不能复杂透视。

====================
四、MVP 核心定位
====================
玩家是 Solmere 邮局异常邮件部门的新任临时邮差。正常邮件不由玩家处理；玩家负责的是无法正常投递、旧地址、地址残损、积压旧信、特殊邮件等“异常件”。

核心不是“送信模拟”，而是：
【观察物证 → 调查人物与地点 → 推断客观收件人/去向 → 决定是否、何时、以什么形式让信息抵达 → 观察后果】

必须把两个层级分开：
A. Deduction：客观推理，谁是正确收件人、地址、时间关系。
B. Intervention：主观干预，送、晚送、暂扣、退回、NPC 代送，极少数特殊件可做有限内容编辑。

玩家可以推理正确但做出道德上有争议的处理，也可以出于善意做错。不要给“善恶值”。

====================
五、MVP 完整循环
====================
试玩只做 1 个工作日，但要完整。

1. 开场：主角到岗，主管用极短对白说明异常件岗位，不做大段教程。
2. 进入邮局工作台：今日 5 封异常件放入托盘。
3. 玩家可任意顺序查看信封正反面、邮戳、旧标签、附件轮廓。
4. 简单件可直接通过地图/环境/档案解决。
5. 特定信件允许拆信。拆信不是一个按钮，要进入实际操作界面。
6. 玩家打开地图，前往已有地点。
7. 在地点内通过点击建筑细节、公告、门牌、时刻表、旧标签、少量 NPC 对话收集线索。
8. NPC 对话量少，但每句信息必须有功能或人文价值。
9. 玩家回到信件或档案界面交叉验证。
10. 投递/延迟/退回/暂扣/NPC 代送。
11. 关键选择必须在同一天看到至少一个可感知后果。
12. 下班结算：不显示精确声望数值，只显示职业状态与事件摘要。
13. Case 05 作为主线钩子结束试玩。

禁止把流程做成固定线性 1→2→3；Case 02–04 至少允许两种解决路径。

====================
六、必须实现的“真实交互”，禁止纯按钮替代
====================
A. 信封检查
- 可拖拽移动。
- 可翻正反面。
- 可局部放大。
- 可将信封与档案/地图/笔迹样本并排。
- 鼠标/触摸指针需要有抓取、释放、悬停反馈。

B. 残损纸片拼合
- 纸片独立刚体/Control 节点，可拖动。
- 接近正确位置时只允许非常轻微吸附，不要自动拼好。
- 旋转角度如果 MVP 工期允许可做 15°/自由旋转；若不允许，使用有限旋转按钮但仍需玩家判断位置。
- 拼合正确后文本可读性提高，不要弹“正确”。

C. 拆信
- 进入独立桌面模式。
- 使用游戏化、非现实教程化的两种工具：安全拆封工具 / 快速拆封工具。
- 快速工具省游戏内时间但更易留下可见裂痕；安全工具耗时更多，痕迹更小。
- 不给现实违法拆信技巧说明。

D. 修复
- 对齐折痕。
- 将破损边缘放回轮廓。
- 使用虚构修复胶带/修复印章。
- 重新封合后玩家可再次放大查看自己的成品。
- 后台记录 tamper_score，但前台只通过画面表现“几乎无痕 / 轻微 / 明显”。

E. 地图
- 点击地点不是纯传送菜单；地图要显示地点关系和时间成本。
- 进入地点后必须有可点环境对象。

F. NPC 代送
- 必须先在地点找到愿意代送的 NPC。
- 交给 NPC 后该封信当天失去“拆信”和“亲自到场观察”机会。
- 这是效率与信息量之间的 trade-off。

====================
七、时间系统
====================
MVP 只做轻量时间，不做复杂交通模拟。
- 工作时间 09:00–18:00。
- 移动到地点消耗 20–50 分钟游戏时间，具体见 data。
- 普通观察不额外扣时。
- 深度调查/厨房支线可扣 20–30 分钟。
- 阅读、思考、打开档案不实时倒计时，避免玩家因为慢读受罚。
- 仅 Case 02 或 03 的急件有明确截止时间。
- 普通件/积压件可跨天，但 MVP 只有一天，因此结算时记为 Pending，不立即失败。

====================
八、声望与信任
====================
后台保留数值，前台隐藏精确数字。
建议后台：postal_reputation 0–100；NPC trust 独立。
前台只显示状态：
- Trusted / 受到信任
- Professional / 专业
- Ordinary / 评价一般
- Questioned / 被质疑
- Under Review / 审查中

成功送达、尊重规则提高；错投、急件逾期、拆信被发现降低。
不要让声望直接决定谜题答案，只影响 NPC 愿意提供多少外围信息。

====================
九、五封信必须按 Puzzle Bible 实现
====================
必须完整实现 Case 01–05，不可偷换成普通按钮任务。

Case 01：旧地名来信
- 教学。
- 不拆信。
- 通过旧地名、社区中心旧标识/公告完成地点对应。
- 立即反馈正确。

Case 02：赶在日落前
- 急件/限时件。
- 通过公交站时间、尘缘信息、观景台行程判断。
- 可以亲自送，也可以交给尘缘代送。
- 两条路径获得不同后续信息。

Case 03：雨水里的邀请函
- 可拆修复件。
- 水损地址碎片拼合。
- 拼出 Rose Court 302 后仍需确认住户是否搬迁。
- 可拆信获得强线索，但必须修复。

Case 04：迟到六年的情书
- MVP 核心。
- 结合旧照片、日期、活动记录、旧门牌、笔迹样本推断寄件人与收件人。
- 少量 NPC 主动提问。
- 客观答案明确，是否投递没有标准答案。
- 允许“投递 / 暂扣 / 退回寄件人”三种主要处理。
- 极少数特殊交互：可选择是否把照片附件一同送出。不要自由重写整封信。

Case 05：写给你的信
- 特殊件/主角件。
- 收件人是主角或“异常邮件岗位的下一位工作人员”。
- 揭示旧异常件并非全部“遗失”，可能曾被前任主动扣留。
- 玩家选择 File / Keep / Destroy 只作为哲学钩子，不要在 MVP 内给出道德判定。

====================
十、人员档案系统
====================
参考 Obra Dinn 的“信息积累与交叉判断”，但 UI 必须原创、简洁、2D。
每个 NPC 仅显示玩家已经确认的信息：
- 姓名
- 头像
- 已知住址
- 常去地点
- 已知关系
- 笔迹样本（若已收集）
- 相关信件编号

未知字段显示空白或“？”；不要把所有潜在信息灰字提前泄露。
核心答案不要每次立刻绿勾确认。Case 04 使用延迟确认。

====================
十一、UI / UX
====================
UI 不得像后台管理软件，也不得像写实办公桌。
- 大块纸张卡片 + 扁平图标 + 少量邮戳/标签。
- 主色：奶油白、青绿、灰蓝、暖橙、少量珊瑚红用于急件。
- 每页只显示当前需要的工具。
- 工具图标必须可拖/点击后进入实际交互，不做装饰。
- 鼠标悬停只给非常轻的纸张抬起/阴影变化，不给发光线索。
- 所有转场 0.2–0.5 秒，避免黑屏等待。

必须实现界面：
1. Title / Continue
2. Post Office Desk
3. Letter Inspect
4. Disassemble & Restore
5. Town Map
6. Location Scene
7. NPC Conversation
8. Personnel Directory
9. End-of-Day Summary

====================
十二、音效与反馈
====================
每个操作都要有反馈：
- 纸张拖动、落下
- 信封翻面
- 邮戳轻敲
- 地图打开
- 纸片拼合吸附
- 修复工具轻触
- 投递完成
- 急件临近截止的很轻微提示音

不要过度 ASMR，不要写实到喧宾夺主。
音乐：海边夏日下午的轻爵士/木吉他/手风琴或轻打击，温暖克制。Case 04/05 只减少乐器和留白，不切恐怖音乐。

====================
十三、缺失素材生成规则
====================
所有缺失素材必须按 `AI_ASSET_GENERATION_PROMPTS.md` 单独生成。
- 背景一张一张独立生成。
- 道具一件一件透明 PNG 生成。
- UI 组件单独生成。
- 新 NPC 若必须生成，必须是新角色，不得借用用户主角/尘缘的脸、衣服、轮廓。
- 不允许“把用户的建筑放进 AI 生成背景里”。用户建筑必须在引擎内作为独立原图层摆放。

====================
十四、工程架构
====================
必须数据驱动，不能把五封信全部硬编码到 UI 脚本。
至少包含：
- LetterData
- NPCData
- LocationData
- ClueData
- GameClock
- ReputationSystem
- DialogueSystem
- MailDeskController
- RepairPuzzleController
- MapController
- CaseState / ChoiceState
- SaveData

所有 Case 状态、线索、去向、可用处理方式从 JSON/Resource 读取。

====================
十五、存档与容错
====================
- 自动存档：每次离开邮局、关键投递、关键选择后。
- 允许手动 Continue。
- 不允许谜题进入死档：即使玩家错投，游戏也要用退信、第二条线索或后续事件继续。
- Case 04/05 的重大决定可以不可逆，但要在操作确认前有自然语义提示，不要弹“你确定吗？这个选择不可逆”这种出戏警告。

====================
十六、完成标准
====================
只有同时满足以下条件才算完成：
1. 从标题进入后可以完整玩到日终结算。
2. 五封信全部能处理且有不同机制。
3. 至少 1 个残损纸片拼图实际可操作。
4. 至少 1 个拆信与修复实际可操作。
5. 至少 1 个 NPC 代送分支。
6. 至少 1 个急件时间压力。
7. 至少 1 个延迟确认的推理。
8. Case 04 有真正的道德分支并产生可见场景/文本后果。
9. Case 05 给出主谜题钩子。
10. 用户锁定素材 hash 未变化。
11. 新增画面严格保持 2D 简约，不出现写实 AI 厚涂或 3D 质感。
12. 不存在开发者占位按钮、DEBUG 文本、未完成占位框。

====================
十七、工作方式
====================
不要先做大而全框架再填内容。按 IMPLEMENTATION_TASK_ORDER 分阶段，每一阶段完成即可运行测试。
开发时优先保证：
可玩性 > 可读性 > 节奏 > 美术统一 > 扩展性。
不要为了“系统很多”牺牲玩家实际操作。

开始执行前，先输出：
- 你识别到的现有项目结构
- 你将复用的现有模块
- 你将新增的文件树
- 你会如何保证 LOCKED 资产不被修改
然后直接开始实现，不要再向用户重复询问已经在本包里说明的问题。
